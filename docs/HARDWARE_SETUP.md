# Hardware setup and first run

## 1. Prerequisites and installation location

Use the same working VFIO-NVMe kernel and QEMU patches as your existing migration PoC. The project does not replace QEMU, create namespaces, attach VFs, or supply new `source.sh`/`DEST.sh` definitions. Those scripts contain your host-specific VM/storage configuration and are deliberately configured by path.

Put the project at `/opt/uvp-control` on each trigger host, or update all absolute paths in `config/hardware.json`. Install Python 3.10+, a distro clang with the BPF backend, build tools, libbpf development files, and OpenSSH. The backend itself uses only the Python standard library.

```bash
cd /opt/uvp-control
make build CLANG=/usr/bin/clang
make test
```

`make build` produces `vendor/uvp-live-fio/bin/uvp-daemon` and `bin/hooks.bpf.o` under that vendor directory. CO-RE requires running kernel/module BTF. The framework is x86-64-specific. Kernel symbol names and synchronous wrapper semantics must match your tree.

For the chosen case:

```bash
./scripts/host-preflight.sh nvmevf_cmd_suspend_device
```

Preflight is read-only and not proof of BPF verifier acceptance. Actual attach occurs when arming. A failure before `READY` must be resolved before migration.

## 2. Configure host transport

Copy `config/hardware.example.json` to `config/hardware.json`. For each of `source` and `destination`, configure:

| Field | Meaning |
|---|---|
| `transport` | `local` or `ssh` |
| `ssh_target` | Host account/address, e.g. `uvp@192.0.2.20`; no password in configuration |
| `ssh_port` | Host SSH port, usually 22 |
| `identity_file` | Key path on the coordinator machine |
| `known_hosts_file` | Preverified known-hosts file on the coordinator |
| `privilege_prefix` | Example `["/usr/bin/sudo", "-n", "--"]`; use `[]` if already running with sufficient privileges |
| `daemon` / `bpf` | Absolute paths on that host |
| `pid` | Actual QEMU host TGID; update for every fresh VM process |
| `controller` | Host PF/admin controller, such as `/dev/nvme0` |
| `cntlid` | Target VF controller ID encoded in migration commands; not the Linux device number |
| `symbols` | Optional mapping of case number strings to audited wrapper symbols |

Example symbol override:

```json
"symbols": {"1": "nvmevf_cmd_suspend_device", "2": "nvmevf_cmd_get_ctrl_state"}
```

**Same machine, two VFs:** set both transports to `local`, and set different QEMU PIDs and appropriate CNTLIDs. The host controller path may be the same PF.

**Two machines:** the coordinator can run on the source. Set the destination transport to `ssh`. Cases 1/2 launch the source daemon; cases 3/4 launch the destination daemon. The coordinator does not run the BPF program remotely through the browser; it executes the native daemon on the selected host over a persistent SSH stdio channel.

SSH uses `-T`, BatchMode, strict known-host checking and keepalives. Test host connectivity and noninteractive daemon privilege access before using the UI. The project does not add sudoers rules or distribute credentials. Daemon actions run with the daemon's privileges. For a local lab session you can run the coordinator with appropriate privileges and set `privilege_prefix` to `[]`; protect the token as access to those operations.

## 3. Configure the existing migration and guest fio scripts

Copy the original `vendor/uvp-live-fio/config/uvp.conf.example` to `config/uvp.conf`. Configure fresh `RUN_ID`, source/destination QEMU IDs, controller IDs, guest SSH routes, key/known-host paths, and a mounted disposable guest test directory.

The root JSON configuration controls the web backend/daemon. The Bash `uvp.conf` controls the existing guest runner scripts. **They are separate; UI target edits do not rewrite `uvp.conf`.** Keep their intended device and run settings consistent.

Each new fio experiment needs a new `RUN_ID`. The launcher intentionally prevents an uncertain duplicate start. The UI's own run ID identifies an audit record; it does not replace the guest `RUN_ID`.

Cross-host cases 3/4 require the same `uvp.conf` and prepared guest identity file on the destination daemon host. Guest endpoints in that config are resolved **from the daemon host**, not the browser or coordinator. Copy the `prepared.status` file generated by preparation into the destination host's matching `$OUTPUT_DIR/$RUN_ID/` directory. For continuity checks also make `pre-migration.status` available to the checking host. The UI does not silently synchronize these files or credentials.

In `hardware.json`, point job profiles to your actual scripts:

- `source` → `/bin/bash /actual/path/source.sh`
- `destination` → `/bin/bash /actual/path/DEST.sh`
- `migrate` → `/bin/bash /actual/path/migrate.sh`
- `prepare`, `prestart`, `verify`, `collect` → supplied scripts plus the configured `uvp.conf` path.

Set `enabled: true` only after configuring a profile. Commands are explicit argv arrays, not browser-supplied shell strings. If your script needs a working directory or environment, make a small operator-owned wrapper that sets them and `exec`s the script. QEMU setup scripts must daemonize/redirect QEMU and return; this is not a foreground QEMU terminal. Migration scripts should return a meaningful exit code and have an appropriate `timeout` in seconds.

## 4. Start the controller

```bash
cd /opt/uvp-control
python3 -m uvp_server.server --hardware --config config/hardware.json --port 8000
```

Use the token printed on its terminal. The controller listens on loopback; use an SSH tunnel to access it from your laptop. No HTTP TLS listener is included; SSH supplies the remote transport. The standard-library HTTP server is intended for a local single-operator lab, not Internet hosting.

The UI connection badge means **API reachable**. Only daemon `READY` proves that its requested BPF programs loaded and attached.

## 5. First checkpoint without a destructive action

1. Launch destination and source using your established order; populate current QEMU PIDs in the UI.
2. Select case 1, source Suspend completion. Set the correct host controller and target VF CNTLID.
3. Leave both actions at `None` for the first checkpoint test. Set a finite hold window, for example 120 seconds.
4. Click **Arm checkpoint**. Wait for `ARMED` / daemon `READY`.
5. Start migration with the UI job or from another terminal using your existing script.
6. Expect submission/completion details, successful wrapper return, syscall exit, `STOP_CONFIRMED` and `HOLD_READY`.
7. Click **Release QEMU**. Confirm SIGCONT and daemon exit 0.
8. Independently check QEMU migration status, destination guest I/O and your data-integrity workload. UI `DONE` alone is not proof of those outcomes.

For subsequent cases start a fresh migration with fresh VM/device state as required by your setup. Choose complete Get on source, complete Set on destination, or destination Resume. A Set→Resume coalesced syscall is rejected if it does not expose the requested boundary; do not bypass that protection.

## 6. Run a host action while held

Choose one host profile before arming. When the UI reaches `PAUSED`, click **Run host action**. The C daemon confirms that the target remains stopped, executes the configured argv, waits for successful completion within both the action and remaining hold budget, then returns to `PAUSED`. Resume is disabled while the action runs.

The host action executes on the **checkpoint daemon host**. To act on a different machine, explicitly configure an SSH-based wrapper on that host. Use a composite script if several ordered actions must run in one hold; return nonzero on failure. Each host action can be triggered once per checkpoint to avoid accidental duplicate resets.

`NVMe reset`: configure the exact controller path, checking whether it names a PF or VF. A PF reset can affect multiple VFs/namespaces. The example `/dev/nvme1` is a placeholder and does not automatically refer to the selected VF.

`VF FLR`: configure the exact BDF. The helper requires `physfn`, temporarily selects `flr` alone in `reset_method`, writes `reset`, then restores the method list. Kernels may reject a reset while VFIO owns the device; that is a failed action, not success. It does not silently fall back to a bus reset.

Custom script example profile:

```json
"source-custom": {
  "label": "My controlled stress sequence",
  "kind": "host",
  "host": "source",
  "enabled": true,
  "description": "Operator-owned test script, executed once while held",
  "argv": ["/opt/uvp-tests/stress-sequence.sh", "--profile", "migration"]
}
```

Do not launch a background child and immediately exit zero if the UI should wait for the operation. The daemon tracks the action process; descendants/remote processes that escape its process group are outside rollback/cleanup guarantees.

## 7. Guest fio modes

**Launch after the selected checkpoint:** prepare the guest first; select the guest fio profile; arm and migrate. While QEMU is stopped, the action is only pending. Release QEMU; the original launcher waits for the configured guest SSH endpoint and acknowledges the launch. Destination is the normal endpoint after stop-and-copy.

**Same fio continues through migration:** prepare the guest, run **Start source fio before migration**, arm the checkpoint, then start migration. After destination activation, run **Verify fio continuity** and **Collect fio results**. A prestarted fio can also be selected as the post-release action: the original idempotent launcher will acknowledge the same run instead of starting a duplicate.

The original sample workload uses 4 KiB direct randrw with 30% reads, depth 8, 256 MiB and 300 seconds. To change fio parameters use `config/uvp.conf` and `vendor/uvp-live-fio/guest/guest-fio.sh`, then prepare again with a new RUN_ID. Use your established CRC verify job when validating data integrity; the default sample has no checksum verification.

## 8. I/O timeout injection

The original `inject_one_timeout_nvme1n1.sh` is bundled unchanged. Its target is fixed to **host-bound nvme1n1**. The profile arms one lost-completion budget and returns; a later host I/O consumes it. `times=1` is a global fault-injection budget and is not exact request selection under concurrent completions. State persists after the script exits. Use the corresponding status/disarm jobs after the run to inspect and restore original settings.

It cannot inject into a guest-owned VF's I/O path from the host because those commands do not traverse the host NVMe block queue. To use Linux timeout injection for that guest, provision and arm an appropriate injector inside the runnable guest before migration. This project does not pretend the host injector affects passthrough I/O.

## 9. Failure and recovery

- Cancel releases the checkpoint and stops its action worker; it does not cancel QEMU migration or undo a reset.
- Host action failure or timeout fails the checkpoint cycle and releases the owned QEMU stop during cleanup. Inspect the device afterward.
- Control stdin EOF/SSH disconnect fails the run and releases the owned stop. SSH outage detection can take the keepalive interval; the daemon's hold watchdog is independent.
- A closed browser leaves the backend running until operator action or deadline. Browser reconnect can inspect the active run.
- Restarting the coordinator marks unfinished database runs `INTERRUPTED`; it never reattaches by numeric PID. Inspect hardware before starting another migration.
- The watchdog's emergency release is roughly hold timeout + 5 seconds from recorded stop intent. The ordinary hold deadline starts at confirmed stop. A blocked/uninterruptible kernel path may prevent process stop/recovery.
- Automatic release is a bounded lab recovery policy, not device rollback. A host/remote command may already have changed hardware.
- There is no QMP status query, migration rollback, or automated storage integrity verdict in this version.

## 10. Extending checkpoint coverage

Changing a wrapper symbol is supported only if it is an audited synchronous int-returning wrapper with zero meaning complete success. The command decoder still recognizes the four original logical command classes. For pre-copy/CDQ/other phases, add a suitable adapter to the BPF decoder/gate and daemon/UI phase registry, then test ownership and exact boundary behavior. Registering a label alone does not implement a new breakpoint.
